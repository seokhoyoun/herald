# VectorRAG 입문: 왜 md 파일 폴더 정리로는 부족할까

우리는 보통 지식을 이렇게 관리합니다.

```
notes/
├── dev/
│   ├── docker-basics.md
│   └── nginx-config.md
├── ai/
│   ├── transformer.md
│   └── loss-function.md
└── etc/
    └── ideas.md
```

폴더를 나누고, 파일 이름을 잘 짓고, 필요하면 `grep`으로 검색합니다.
꽤 잘 동작하는 것 같지만, 여기엔 근본적인 한계가 있습니다.

**"컨테이너가 자꾸 죽는 이유"를 찾고 싶은데, 문서에는 "OOM으로 프로세스가 종료됨"이라고 적혀 있다면?**

`grep "컨테이너가 죽는"`은 아무것도 찾지 못합니다. 단어가 다르기 때문입니다.
사람은 두 문장이 같은 이야기라는 걸 알지만, 문자열 검색은 모릅니다.

이 문제를 푸는 것이 바로 **Vector RAG**입니다.

## 1. RAG란 무엇인가

RAG(Retrieval-Augmented Generation)는 이름 그대로 세 단계입니다.

1. **Retrieval(검색)**: 질문과 관련 있는 문서를 찾아온다
2. **Augmented(증강)**: 찾아온 문서를 LLM의 프롬프트에 끼워 넣는다
3. **Generation(생성)**: LLM이 그 문서를 근거로 답변을 만든다

LLM은 학습 시점 이후의 정보나 여러분의 개인 노트를 모릅니다.
그렇다고 매번 노트 전체를 프롬프트에 넣을 수도 없습니다. 컨텍스트 창은 유한하고, 토큰은 비용이니까요.

그래서 **"질문과 관련된 부분만 골라서 넣어주자"**는 것이 RAG의 핵심 아이디어입니다.
문제는 "관련된 부분"을 어떻게 찾느냐인데, 여기서 벡터가 등장합니다.

## 2. 용어 정리: 청크, 임베딩, 벡터 DB

### 청크(Chunk)

문서를 통째로 다루기엔 너무 큽니다. 그래서 잘게 나눕니다.
이렇게 나눈 조각 하나하나를 청크라고 부릅니다.

```
docker-basics.md (10,000자)
  → 청크 1: "Docker 컨테이너는 격리된 프로세스로..." (500자)
  → 청크 2: "메모리 제한을 초과하면 OOM Killer가..." (500자)
  → 청크 3: "볼륨 마운트는 데이터 영속성을..." (500자)
```

왜 나눌까요?

- **검색 정밀도**: 질문과 관련 있는 건 문서 전체가 아니라 특정 문단입니다. 문서 단위로 찾으면 관련 없는 내용까지 딸려옵니다.
- **컨텍스트 절약**: LLM에게는 꼭 필요한 조각만 주는 것이 좋습니다.

청크를 나누는 전략도 여러 가지입니다. 글자 수로 자르기, 문단 단위로 자르기, 마크다운 헤딩 기준으로 자르기 등이 있고, 보통 앞뒤 청크가 조금씩 겹치게(overlap) 잘라서 문맥이 끊기는 것을 방지합니다.

### 임베딩(Embedding)과 임베딩 모델

임베딩은 **텍스트를 숫자 배열(벡터)로 바꾸는 것**입니다.

```
"컨테이너가 자꾸 죽어요"
  → [0.12, -0.83, 0.45, ..., 0.07]  (예: 1536개의 숫자)
```

핵심은 이 변환이 아무렇게나 이루어지지 않는다는 점입니다.
**의미가 비슷한 문장은 비슷한 벡터가 되도록** 학습된 모델이 변환을 담당하는데, 이것이 임베딩 모델입니다.

- OpenAI `text-embedding-3-small`
- 오픈소스 `BGE-M3`, `multilingual-e5` 등

임베딩 모델 덕분에 이런 일이 가능해집니다.

```
"컨테이너가 자꾸 죽어요"        → 벡터 A
"OOM으로 프로세스가 종료됨"     → 벡터 B
"김치찌개 맛있게 끓이는 법"     → 벡터 C

거리(A, B) = 가깝다   ← 단어는 다르지만 의미가 비슷
거리(A, C) = 멀다     ← 의미가 전혀 다름
```

단어가 하나도 겹치지 않아도, 의미가 비슷하면 벡터 공간에서 가까이 놓입니다.
이것이 문자열 검색과의 결정적 차이입니다.

### 벡터 DB(Vector Database)

청크마다 임베딩 벡터를 만들었으면, 이걸 저장하고 빠르게 검색할 곳이 필요합니다.
그 역할을 하는 것이 벡터 DB입니다.

- 전용 솔루션: Pinecone, Qdrant, Milvus, Chroma
- 기존 DB의 확장: PostgreSQL의 `pgvector`, SQLite의 `sqlite-vec`

벡터 DB의 핵심 기능은 하나입니다.
**"이 벡터와 가장 가까운 벡터 N개를 찾아줘"** (유사도 검색, Similarity Search)

가깝다는 것은 보통 **코사인 유사도(cosine similarity)**로 측정합니다.
두 벡터가 이루는 각도가 작을수록(방향이 비슷할수록) 의미가 비슷하다고 봅니다.

청크가 수십만 개여도 전부 일일이 비교하지 않도록, HNSW 같은 근사 최근접 이웃(ANN) 인덱스를 사용해 밀리초 단위로 검색합니다.

## 3. 전체 동작 원리

이제 조각을 맞춰 봅시다. Vector RAG는 두 단계로 나뉩니다.

### 준비 단계 (Indexing) — 한 번만

```
문서들 → ① 청크로 분할 → ② 임베딩 모델로 벡터화 → ③ 벡터 DB에 저장
```

1. md 파일들을 청크로 나눕니다
2. 각 청크를 임베딩 모델에 통과시켜 벡터로 만듭니다
3. 벡터와 원문 텍스트를 함께 벡터 DB에 저장합니다

### 질문 단계 (Query) — 질문할 때마다

```
질문 → ① 같은 임베딩 모델로 벡터화
     → ② 벡터 DB에서 가장 가까운 청크 N개 검색
     → ③ 검색된 청크 + 질문을 LLM에 전달
     → ④ LLM이 청크를 근거로 답변 생성
```

프롬프트는 대략 이런 모양이 됩니다.

```
다음 문서를 참고해서 질문에 답하세요.

[문서 1] 메모리 제한을 초과하면 OOM Killer가 컨테이너를 종료시킨다...
[문서 2] docker stats로 메모리 사용량을 확인할 수 있다...

질문: 컨테이너가 자꾸 죽는데 왜 그럴까?
```

LLM은 자기 기억이 아니라 **눈앞에 주어진 문서를 근거로** 답합니다.
그래서 환각(hallucination)이 줄고, 출처를 함께 보여줄 수도 있습니다.

한 가지 중요한 규칙: **저장할 때 쓴 임베딩 모델과 검색할 때 쓰는 임베딩 모델은 반드시 같아야 합니다.** 모델이 다르면 서로 다른 좌표계에 있는 셈이라 거리 비교가 무의미해집니다.

## 4. 왜 디렉토리 + md 파일 관리보다 효율적인가

이제 처음 질문으로 돌아갑니다. 폴더 정리와 무엇이 다를까요?

### 첫째, 의미로 찾는다 vs 문자로 찾는다

디렉토리 구조와 `grep`은 **문자열이 일치해야만** 찾습니다.

- "컨테이너 죽음" ≠ "OOM 종료" → 검색 실패
- 영어 문서에서 한국어로 검색 → 실패
- 오타 하나 → 실패

벡터 검색은 **의미**로 찾습니다. 표현이 달라도, 언어가 달라도(다국어 임베딩 모델 기준), 의미가 가까우면 찾아냅니다.

### 둘째, 분류는 하나지만 의미는 여러 개다

폴더 구조의 고질적인 문제는 **한 문서는 한 폴더에만 들어간다**는 것입니다.

"Docker 컨테이너의 메모리 튜닝" 문서는 `dev/docker/`에 둘까요, `dev/performance/`에 둘까요?
어디에 두든 나중에 반대쪽 관점으로 찾을 때 놓치게 됩니다.

벡터 공간에서는 분류 자체가 필요 없습니다. 문서는 자기 의미에 해당하는 좌표에 놓일 뿐이고, 어떤 관점으로 질문하든 그 관점과 가까우면 검색됩니다. **분류 체계를 설계하고 유지하는 비용이 통째로 사라집니다.**

### 셋째, 찾은 다음이 다르다

grep으로 파일을 찾으면 그다음은 사람의 일입니다. 파일을 열고, 스크롤하고, 읽고, 종합해야 합니다.

RAG는 검색 결과가 곧바로 LLM의 입력이 되어 **"여러 문서를 종합한 답변"**이 나옵니다.
세 개의 문서에 흩어져 있는 정보라도 하나의 답으로 정리됩니다.

### 넷째, 규모가 커져도 사람의 부담이 늘지 않는다

| | 디렉토리 + md | Vector RAG |
|---|---|---|
| 검색 기준 | 파일명, 문자열 일치 | 의미 유사도 |
| 분류 | 사람이 폴더 설계·유지 | 불필요 (자동으로 벡터 공간에 배치) |
| 동의어/표현 차이 | 못 찾음 | 찾음 |
| 문서 1만 개일 때 | 폴더 구조가 무너짐 | 검색 품질 유지 |
| 결과 활용 | 사람이 열어서 읽음 | LLM이 종합해 답변 |

노트가 100개일 때는 폴더 정리로 충분합니다.
하지만 1,000개, 10,000개가 되면 "어느 폴더에 넣었더라"와 "뭐라고 적었더라"가 병목이 됩니다.
벡터 검색은 문서가 늘어나도 **찾는 방식이 그대로**입니다. 질문만 하면 됩니다.

### 그럼 폴더 관리는 버려야 할까?

아닙니다. 둘은 대체 관계가 아닙니다.

- 원본은 여전히 md 파일로 관리합니다 (git 버전 관리, 편집 편의성)
- 벡터 DB는 그 위에 얹는 **검색 인덱스**입니다

파일이 바뀌면 해당 청크만 다시 임베딩해서 갱신하면 됩니다.
말하자면 md 디렉토리가 원본 저장소이고, 벡터 DB는 "의미로 찾을 수 있게 만든 색인"입니다. 책은 책장에 꽂아두되, 아주 똑똑한 사서를 고용하는 셈입니다.

## 5. 정리

- **청크**: 문서를 검색하기 좋은 크기로 자른 조각
- **임베딩 모델**: 텍스트를 "의미가 비슷하면 가까운" 숫자 벡터로 바꾸는 모델
- **벡터 DB**: 벡터를 저장하고 유사도 검색을 빠르게 해주는 저장소
- **RAG**: 질문과 의미가 가까운 청크를 찾아 LLM에게 근거로 주고 답변을 생성하는 구조

디렉토리 관리가 "사람이 분류하고 사람이 찾는" 방식이라면,
Vector RAG는 "의미가 스스로 자리를 잡고, 질문이 곧 검색이 되는" 방식입니다.

지식이 쌓일수록 격차는 벌어집니다. 폴더 이름을 고민하는 대신, 질문을 던지세요.
